# 实际问题、判断依据与修复

本文记录参考板开发过程中出现过的问题，说明当时如何判断和处理。它不是所有同名报错的通用结论。版本不同、固件不同，应重新收集证据。

## 1. 桌面应用打开约两秒后消失，后台仍在

**现象**：第一次点图标或桌面语音唤醒时，窗口短暂出现又回到桌面；有时要点多次，后台模型、网页或语音进程却仍然运行。这里“约两秒”是现场观察，不是已经证明的统一系统超时参数。

首先区分三种情况：

| 证据 | 更可能表示什么 |
| --- | --- |
| 进程仍在，APP_FOCUS active=false，没有 WINDOW_EXIT | 窗口失去焦点/被桌面覆盖，不能称为进程崩溃 |
| APP_EXIT_REQUEST、APP_EXIT_DONE、WINDOW_EXIT code=0 | 走了应用自己的正常退出路径，继续追查谁发起退出 |
| 非零退出码、信号退出、OOM/段错误日志 | 实际异常退出，需要另外排查内存、动态库或程序错误 |

参考板的屏幕不是普通 PC 桌面，而是原厂 SystemUI 在管理应用。单独创建一个能显示 QML 的窗口，只解决了画面；应用的启动登记、冷启动/再次打开、状态询问、退出返回都还要配合原厂流程。

### 原因一：窗口没有正确实现原厂状态协议

早期只用通用窗口或浏览器启动器，未完整配合原厂的应用管理。后来加入 Qt/C++ 原生宿主，连接本机 Qt Remote Objects 的 SystemUICommonApi。

最初假设接口是 QByteArray，实际检查到本板的信号与方法为：

```text
serverSendVariant(QString,int,int,QVariant)
onServerVariant(QString,int,int,QVariant)
```

仅建立连接也不等于协议完成。需要正确的类型、命令和参数传输，在动态副本初始化后匹配签名，并完成应答。我们先增加只读接口检查和隔离自测，再实现本板四参数协议；兼容代码另保留已识别的字节数组协议。

当前宿主发送对应启动控制，回答状态/已有实例查询，处理显示、退出和返回桌面。正常日志可见 SYSTEMUI_CONNECTED、SYSTEMUI_SHOW_ACK、SYSTEMUI_EXISTING_REPLY、SYSTEMUI_HEARTBEAT_REPLY、SYSTEMUI_RETURN_HOME。

### 原因二：后台唤醒绕过了原厂的启动登记

即使从图标正常打开，后台直接创建助手进程仍可能绕过原厂桌面自己的“当前应用”和 QProcess 管理，导致桌面状态与真实窗口不一致。

修复后，后台不再直接冒充原厂桌面创建应用，而是通过本机、限于该助手的 socket 请求桥接。桥接只在真正的 `/opt/ui/systemui` 进程中启用，调用该固件现有的 QML callApp 方法，由原厂完成登记和冷/热启动。窗口出现后再由原生宿主继续状态通信。

```text
原厂图标：SystemUI callApp → 原厂登记/启动 → 原生宿主状态通信
桌面唤醒：待唤醒程序 → 本机桥接 → 同一个 callApp → 同一套后续流程
```

桥接仅给 SystemUI 这一条启动命令加载，随后清除自身预加载设置，避免传给子应用。没有替换原厂二进制。入口脚本使用前台 exec，让原厂 QProcess 跟踪的生命周期覆盖整个助手窗口；不能创建窗口后立刻结束入口进程。

**准确说法**：“把自研助手接入原厂桌面的应用管理与启动流程，像原厂应用一样被管理。”它仍是我们维护的自研程序，不是变成厂商出品的软件。也不能把所有闪退都归因于同一个机制。

### 当时没有足够证据支持的判断

`event processing lagging behind by 11～20ms` 是输入事件处理延迟警告；它不能单独证明这个窗口为什么消失。减少负载可能改善触控，但本次关键修复是原厂启动登记和状态协议，不是隐藏警告或不断增加启动延时。

复现时同时看 qml-assistant.log、desktop-wake.log、窗口/语音状态文件、进程及退出码，按 [桌面教程](DESKTOP_SETUP.md) 和 [待唤醒教程](WAKE_AND_BOOT.md) 分层检查。

## 2. 图标始终没有出现在屏幕

把 .desktop 文件复制到 /root/Desktop 或配置 Weston 启动图标，对这个屏幕上的原厂应用网格不起作用。检查进程后确认实际桌面是 /opt/ui/systemui，并找到 ATK-DLRK3588/apk1.cfg、apk2.cfg、apk3.cfg。

修复：把脚本安装到原厂 apps 目录、准备 PNG 图标、登记一条匹配的应用清单；备份并正常重启加载。不是重新创建多个桌面进程。

## 3. 重复点击后多窗口、打不开或退出不正常

入口很快结束、后台化启动、重复实例和过期锁记录都可能造成表现相似的问题。修复包括：原厂状态应答、固定进程名与应用名、窗口监督进程持有单实例锁、入口前台 exec，以及按 PID/启动时间/命令核对定向停止。

锁文件存在不等于锁仍被持有；不能一看到文件就删除或按里面的旧 PID 杀进程。模型、网页、窗口、麦克风分别有自己的状态和锁。

## 4. 缺少 libgomp，取得库后又出现 GLIBC 不匹配

ldd 最初显示 libgomp.so.1 not found。它是推理库需要的 GNU OpenMP 运行库，不是语言模型。启用 SDK 配置后仍需确认实际工具链是否生成对应 ARM 产物，不能只看配置项为 y。

后来取得的一个 ARM 库要求 GLIBC_2.38，而板端只有 2.37，所以仍不能加载。最终使用兼容板端 glibc 的库，放入程序自己的库目录，通过 ldd 和 ctypes 加载验证。没有直接覆盖系统 libc。

经验：CPU 架构相同还不够，运行库符号版本也要匹配；内核版本和 glibc 版本不是同一个东西。

## 5. 源码 NPU 驱动版本与板上版本不一致

SDK 源码曾显示 0.9.6，板端实际运行仍为 0.9.2；编译日志成功不表示板上已经换成新内核。该驱动当时配置为内置 y，因此找不到独立 rknpu.ko 是正常情况。

以后按实际 uname、debugfs 驱动版本和真实推理核对。当前已验证参考环境是 Linux 5.10.209、RKNPU 0.9.8、固定官方 RKLLM Runtime 1.3.0。更换驱动不代表所有模型自动兼容，保留恢复路径并重测。

## 6. 下载失败却以为模型已经准备好了

出现过 wget 不支持 HTTPS、DNS 失败、证书信任失败，以及空文件仍保留目标文件名的情况。空文件的 SHA-256 不是模型成功下载的证据。

修复：在能正常访问官方来源的电脑下载，检查长度和文件类型，传输前后比较 SHA-256；修复网络和信任问题，不关闭证书验证。模型二进制和匹配分词器目录分别准备。

## 7. SCP 传到一半断开

WiFi/SSH 断连会留下部分文件，进度显示到 100% 附近也不能代替接收端校验。确认网络和空间后重新传输，比较两端哈希；大文件需要时采用真正支持续传的工具。SSH 保活只能帮助发现/维持连接，不能保证传输绝不失败。

## 8. tar 解压不支持 -j

Buildroot 的 BusyBox tar 未启用 bzip2 选项。修复：用 Python bz2/tarfile，或电脑解压后传完整目录。新教程的 Python 解压块检查预期目录、路径和文件类型；不能把解压失败当模型文件缺失。

## 9. arecord 返回 1，但录音实际完整

该固件上出现过正常录下 WAV、退出码却为 1 的情况，严格 check=True 会把有效录音当成失败。修复：保留实际错误输出，同时检查 WAV 头、采样格式、帧数与时长；产物无效仍报错。只放宽退出码却不验证产物会掩盖真正的录音失败。

连续录音还需检查设备占用、声卡名称和 EOF；不能把所有 arecord 失败都按这一特殊情况放行。

## 10. 声音变小、音量键与屏幕数值不一致

原厂共享音量文件是 0～100；ES8388 的 PCM 原始刻度则可为 0～192，并含 dB 关系。曾出现屏幕 100，而硬件 PCM 仍为 126 的情况。百分比和原始刻度不能直接互换。

当前用原厂共享文件同步界面和播放软件增益，保留硬件增益的独立含义；首次实体按键变化交给原厂 sysvolume，长按逻辑避免重复叠加。重绘时复用控件和稳定状态，减少按钮闪烁。最大音量还取决于实际硬件增益、功放和喇叭。

## 11. 生成、合成太慢，句间有啪声

长思考、等待完整回答后再合成、逐段打开关闭播放设备都会增加延迟。修复：识别后使用流式回答，过滤思考内容，分段合成并按序播放，同一轮尽量共用一个连续 PCM 流，对音频边缘与增益变化做柔化。

过滤思考只是不播报它，不会让 R1 停止计算思考。最前后仍可能有声卡/功放开关声，未宣称已经完全消除。回答提前结束还要分别检查模型 token 上限、播报字数上限和网络流是否真正 done。

## 12. 桌面待唤醒与前台抢麦克风、旧状态干扰

修复包括：麦克风租约锁，带唯一 token、时效和进程出生时间的交接记录；后台确认前台接管后释放设备，退出后恢复待机。前台与后台不能只凭一个 JSON 文件的旧状态判断对方仍活着。

更新包也曾出现安装器期望 0.7.0、实际加载的模块仍为 0.6.0。通过输出 __file__、同时核对入口和依赖模块版本来定位，补齐真正的文件后再激活；只改版本字符串不能替代代码更新。

## 13. 网页更新失败、PID 被复用、开机接口未就绪

曾遇到旧 PID 文件对应的进程已退出，系统把编号分配给别的进程。处理方式是拒绝继续发信号，并核对命令、启动时间及 pidfd；不是强杀该编号。

另一次启动桥接安装因 8081 尚未运行而失败，不能据此说 Qt 桥接必然有问题。修复控制服务启动与就绪等待，再按“模型 → 网页 → 桥接检查 → 后台待唤醒”顺序验收。回退启动旧服务时也需等待接口真正就绪。

## 14. 重启后看起来失联

参考板曾自动连上另一个已保存 WiFi，导致 IP 改变。通过串口确认实际网络，再调整对应自动连接选择；没有为此重刷模型或重装助手。

区分服务没启动、网络变了和客户端用旧 IP。重启后先看串口/板载屏幕的实际地址和进程，再检查各层日志。
